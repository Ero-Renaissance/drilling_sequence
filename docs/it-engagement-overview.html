Drilling Sequence Planner · IT Engagement Brief

One place to plan, sequence, and approve every drilling campaign

The Drilling Sequence Planner is Renaissance's internal system of record for rig scheduling and formal plan approval. This page walks through the application end to end — who can do what, how a plan becomes an approved record, and the security posture behind it.

Internal web application Microsoft single sign-on Full audit trail No external services
Access model

Everyone can see the plan. Few can change it. Fewer can approve it.

Access is enforced on the server for every request — the interface only mirrors it. All sign-in goes through the company Microsoft (Azure AD) tenant; the application stores no passwords and issues no credentials of its own.

Admin

Azure AD role or allowlist

Curates who may plan, manages users, and can act on any campaign. Admin is granted at sign-in from the company directory — the app can add admins but a directory grant can't be silently revoked inside the app.

Planner

Granted by an admin

Holds the global planner grant: may create campaigns and edit the plans they are a planner on. Revoking the grant removes planning rights on every campaign immediately, mid-session.

Reviewers & approvers

Designated per campaign, by email

The required-signature lists for a campaign's plan. Signing authority comes only from designation — being able to view or even edit a plan grants no authority to sign it.

Everyone else

Any signed-in employee

Read-only visibility across all campaigns: the sequence chart, readiness, contracts, revision history, and audit trail. No membership requests, no editing, no approval powers.

End-to-end workflow

From sign-in to an approved, immutable plan

  1. 1 Everyone

    Sign in with Microsoft

    Users authenticate with their company Microsoft account (single sign-on). First sign-in creates their user record automatically with read-only access — there is no separate registration or password.

    Single-tenant Azure AD; tokens are validated server-side on every request (signature, audience, issuer, expiry). Guest accounts are rejected unless explicitly enabled.

  2. 2 Admin

    Grant planning rights

    On the Admin page, an admin grants "planner" to the people who own the drilling schedule. Every grant and revocation is logged with who did it, to whom, and when.

  3. 3 Planner

    Create a campaign and build the plan

    A planner creates a campaign (e.g. a field's quarterly drilling programme) and builds the sequence: well activities with dates, rigs and hydraulic workover units, readiness checks (FDP, LLI, location, funding, EIA and more), rig and HWU contract windows, and flood-risk classification. The Gantt chart, data grid, and print view all read from the same plan.

    Campaigns can also be cloned quarter-to-quarter, carrying activities, readiness, contracts, and signer lists forward. Co-planners can be added — but only people who already hold the planner grant.

  4. 4 Planner

    Submit a revision — the plan freezes

    Submitting takes an immutable snapshot of the plan (a numbered revision) and locks all editing while the decision is pending. Depending on the campaign's review policy, the revision routes through a technical review stage first or goes straight to approval.

    Locked means locked: every editing surface — activities, imports, contracts, readiness — is refused by the server until a decision is made.

  5. 5 Reviewers

    Technical review (optional stage)

    Every designated reviewer must sign before the revision advances to approval. A reviewer who finds problems requests changes with a written reason — the revision returns to the planner and the plan unlocks for rework.

  6. 6 Approvers

    Formal approval

    Every designated approver must sign. Approvers can approve, reject (final), or request changes — declines always require a written reason. The person who submitted a revision can never review, approve, or reject it, even if they are an admin: separation of duties has no bypass.

    A revision with no designated approvers can never approve itself, and submission is blocked if the submitter is the only eligible signer.

  7. 7 System of record

    Approved — and still locked

    Approval does not unlock the plan. The approved snapshot is the binding record, so the live plan cannot drift from what was signed. When the schedule genuinely changes, a planner explicitly reopens it ("Revise Plan" — itself an audited event) and the next revision goes through the same review and approval cycle.

Governance & security

What IT should know

Identity is the company directory

Azure AD single sign-on only (SPA + PKCE flow, v2 tokens). No local accounts, no stored passwords, no API keys issued to users. Admin can come from an AD app role, so joiner/leaver processes stay in the directory.

Fail-closed in production

With ENVIRONMENT=production, the server refuses to start if the development auth bypass is enabled or Azure AD credentials are missing. Guest access is off unless explicitly configured.

Authorization on every request

Every endpoint enforces its own rule server-side: writes require the planner role and the current grant; signing requires designation. Permissions are read fresh from the database per request — a revocation takes effect on the very next call.

Append-only audit trail

Submissions, signatures, approvals, rejections, reason texts, signer-list changes, planner changes, policy changes, and plan reopenings are recorded as governance events. The log has no update or delete path.

Separation of duties

The author of a revision cannot sign it — not as reviewer, not as approver, not as admin. Enforced in the backend with no override.

No data leaves the network

No external SaaS, no telemetry, no CDN dependencies. Email notification is optional and points at the internal SMTP relay. Logs carry identifiers, never tokens, passwords, or personal data.
